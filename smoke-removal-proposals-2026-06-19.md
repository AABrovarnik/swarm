## 2. Минимальная архитектура

Без Kubernetes, без LangGraph. Только 4 простых контура:

1. **Ingress Веня**
   - создаёт задачу в Core;
   - пишет `task_id`, `capability`, `risk`, `deadline`, `attempt_id`.
2. **Core**
   - хранит append-only `task_events`;
   - выдаёт `claim`;
   - управляет `lease/TTL`;
   - хранит `ACK`, `heartbeat`, `outcome`, `escalation`.
3. **Workers**
   - `student`: дешёвые, безопасные, шаблонные операции;
   - `tesla`: инженерные разборы, отчёты, проверка гипотез;
   - каждый worker берет только своё `capability`.
4. **Trusted exporter**
   - отдельный процесс/сервис;
   - читает уже **accepted** artifact;
   - проверяет границы, пишет commit, пушит в GitHub;
   - LLM не имеет `push`-права и не видит секреты публикации.

Правило простое: **Core решает, кто может работать, worker решает только как работать**.

## 3. Целевая схема маршрута

`Веня -> Core -> routing -> claim -> ACK -> lease -> work -> outcome -> accept -> exporter -> GitHub`

Обязательные поля задачи:

- `capability`
- `risk`
- `assignee`
- `attempt_id`
- `lease_owner`
- `lease_expires_at`
- `next_checkpoint_at`
- `deadline`
- `escalation_level`

Минимальные статусы:

- `RECEIVED`
- `ROUTED`
- `CLAIMED`
- `ACKED`
- `IN_PROGRESS`
- `SUBMITTED`
- `ACCEPTED`
- `BLOCKED`
- `FAILED`
- `EXPIRED`

## 6. Тесты

Минимальный набор:

- unit:
  - routing matrix;
  - lease expiry;
  - dedup по `task_id + attempt_id`;
  - exporter gate;
- integration:
  - claim/ACK/TTL cycle;
  - one task, one worker;
  - accepted artifact -> commit;
- failure:
  - worker restart during lease;
  - GitHub push failure;
  - duplicate ingress;
  - split-brain attempt between P0/P1.

## 7. Rollback

- если routing ломается:
  - вернуть старую схему назначения;
  - отключить новый claim path;
  - сохранить append-only events;
- если exporter ломается:
  - заморозить публикацию;
  - оставить accepted artifacts pending;
  - не разрешать ручной push из LLM;
- если cutover P0/P1 ломается:
  - остановить новый live-контур;
  - переключить обратно на `P0`;
  - сверить task state и удалить дубли через reconciliation, не вручную в обход Core.

## 8. Как не допустить >3 одновременных блокеров

Вводим жёсткий WIP-limit:

1. На уровне Core: максимум **3 active blockers** суммарно.
2. Если блокер `BLOCKED` дольше TTL, он обязан либо:
   - перейти в `EXPIRED/FAILED`,
   - либо быть эскалирован Изе.
3. Новый `high-risk` task не запускается, пока не освобождён слот.
4. Любой `duplicate` или `unknown capability` идёт в reject, а не в бесконечный retry.

Это не бюрократия, а предохранитель от нового пожара.

## 9. Риски

- риск 1: неверная маршрутизация capability;
- риск 2: lease без реального ACK;
- риск 3: exporter начнёт публиковать неaccepted artifact;
- риск 4: P0/P1 разойдутся и создадут дубли;
- риск 5: “active service” снова будет спутан с “работает”.

## 10. Критик-проход

Найдены и исправлены противоречия:

1. **Противоречие:** хотели одновременно “быстро” и “безопасно”, но без WIP-limit.  
   **Исправление:** добавлен лимит на 3 одновременных блокера.
2. **Противоречие:** exporter мог бы запускаться LLM-ом “под честное слово”.  
   **Исправление:** экспортёр отделён как trusted process без права `push` у LLM.
3. **Противоречие:** P0 и P1 могли оставаться оба live “на всякий случай”.  
   **Исправление:** один live-контур, второй только shadow/read-only до cutover.
4. **Противоречие:** `systemd active` мог выдаваться за здоровье контура.  
   **Исправление:** приёмка завязана на `claim/ACK/lease/outcome`, а не на активный юнит.

## 11. Итог

Если коротко: сначала фиксируем контракт и routing, затем запускаем worker-цикл с lease, потом выносим trusted exporter, и только после этого сводим P0/P1 в один живой контур. Без этого “дымовая завеса” просто переедет на следующий день.
