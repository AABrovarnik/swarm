Проведи red-team review предлагаемой архитектуры отказоустойчивой системы AI-агентов v3, развёртываемой на выделенном Linux-сервере с уже установленным OpenClaw. **Не соглашайся автоматически, ищи способы её сломать.** Все предложения обосновывай, а не утверждай голословно.

## 2. Контекст и исходные ограничения

### 2.1 Что случилось (исходный инцидент)

Единственный LLM-провайдер достиг лимита на 37 часов. Одновременно перестали отвечать все агенты, фоновые задания и smoke-check. Пользователь получал множество одинаковых технических ошибок вместо полезных результатов. **Корневая причина**: vendor lock-in + отсутствие fail-over + отсутствие WATCHDOG, который заметил бы проблему за минуты, а не за часы.

### 2.2 Целевой профиль потерь

- **30% агентов** в неделю могут упасть на **2–3 дня** с последующим восстановлением.
- Причины: исчерпание провайдерских лимитов, региональные сбои облаков, баны в Telegram/Discord, аппаратные сбои VPS, security-инциденты.
- Рой должен **выживать** в этих условиях, не теряя данные и не «умирая молча».

### 2.4 Платформа

- **Сервер**: выделенный (см. `server-spec-and-software.md`).
- **OpenClaw 2026.6.1** уже установлен: `gateway` слушает `127.0.0.1:18789`, режим `local`, токен авторизации в `~/.openclaw/openclaw.json`, профиль `coding`, активен плагин `ollama`.
- **OpenClaw skills в проде**: только `ollama` и `model-usage`. `coding-agent`, `tmux`, `himalaya` — **отключены на уровне runtime** (security).
- **Модели в OpenClaw**: `ollama/gemma4` (128k context, 8k max tokens) и `ollama/glm-5.1:cloud` (по умолчанию primary).
- **Tools**: `web.search` через `ollama` с domain-whitelist, `db.query` (только SELECT к фиксированным таблицам).

### 2.5 Размер роя

**3 активных LLM-агента + 1 процедурный оркестратор Venya Core:**

- **Izya-Speedy** — быстрые и обратимые задачи.
- **Izya-Deep** — сложные и рискованные задачи.
- **Moysha++** — независимый критик + резерв на другом LLM-провайдере.
- **Venya Core** — **не LLM-агент**, а Python-процесс с правами только `HOLD | QUEUE | STATUS | ESCALATE`.

## 3. Предлагаемая архитектура v3

### 3.1 Лидерство (single Venya Core)

1. **В каждый момент существует ровно один командир.** Выбирается из пула `[Izya-Deep, Izya-Speedy, Moysha++]` по приоритету `Deep > Speedy > Moysha++`. Venya Core **не выбирает командира** — он только **обслуживает** выбранного.
2. **Single Venya Core** на VPS-1, без второго инстанса. systemd `Type=notify`, юнит считается `active` только после `sd_notify(READY=1)`. `/readyz` и `/healthz` — отдельные эндпоинты.
3. **Защита от split-brain**: один процесс + один лидер одновременно, проверить невозможно (потому что нет параллельного инстанса). Если процесс упал — systemd перезапустит за ≤30 сек. Cold start с `litestream`-реплики на VPS-2 за ≤10 мин.
4. **Нет fencing token, нет epoch** (они не нужны для single-leader). Есть `decision_id` (monotonic) + `prev_decision_hash` (Ed25519, hash-chain) — для обнаружения рассинхронизации.
5. **Вернувшийся старый командир не получает власть автоматически.** Если Venya Core перезапустился, лидерство начинается с приоритета `Deep > Speedy > Moysha++` (т.е. сначала попытка Deep, если он жив).

### 3.2 Передача командования (один пакет)

```json
{
  "from": "izya-deep",
  "to": "moysha",
  "goal": "Завершить индексирование репозитория X к 18:00",
  "state": "обработано 4123/8000 файлов, текущий шаг: линтинг Python-файлов",
  "restrictions": ["не отправлять email", "не трогать /etc", "не превышать $5 расходов"],
  "next_action_type": "db_write",
  "next_action_payload": {"table": "decisions", "row": {...}},
  "decision_id": 8731,
  "prev_decision_hash": "a3f2...",
  "ts": "2026-06-14T14:33:21Z"
}
```

**Изменения v3:**
- `next_action_type` ∈ `{db_write, http_get, send_email_sev1, none}` — enum, а не свободная форма.
- `next_action_payload` — структурированные параметры, **не** строка.
- `prev_decision_hash` — Ed25519-подпись предыдущего решения; верифицируется при приёме пакета.
- Преемник обязан:
  1. Проверить `decision_id` > `last_known_id` в БД.
  2. Верифицировать `prev_decision_hash` (Ed25519-подпись).
  3. Подтвердить понимание **коротким ответом** (≤ 200 токенов).
  4. Только после этого получить мандат (запись в `leadership_log`).

### 3.3 Иерархия исполнителей и привязка к LLM

| Агент | Primary LLM | Backup 1 | Backup 2 | Локальный fallback |
|---|---|---|---|---|
| **Izya-Speedy** | `claude-haiku-4.5` | `gpt-5-mini` | — | `ollama/llama3.1:8b` |
| **Izya-Deep** | `claude-sonnet-4.6` | `gpt-5` | `gemini-2.5-pro` | `ollama/glm-5.1:cloud` |
| **Moysha++** | `gemini-2.5-pro` | `claude-sonnet-4.6` (другой аккаунт) | — | — (критик обязан быть облачным) |

**Изменения v3:**
- Moysha++ может работать на **другом аккаунте Anthropic** (2-account strategy), не на другом провайдере.
- **DeepSeek отключён** (GDPR Chap. V: трансграничная передача в Китай без SCC).
- Решение «какого провайдера использовать» — функция Venya Core (таблица `provider_priority`), а не агента.

### 3.4 Хранение состояния и подписи

- **Всё долговечное** — в SQLite (WAL, `synchronous=FULL`) по пути `/var/lib/venya/context.db`.
- **Ed25519-подписи**: каждая запись в `decisions` подписывается приватным ключом Venya Core (хранится в `/root/venya/keys/ed25519.priv`, права 0600, owner `root`). Verify при каждом read.
- **Структура таблиц**:
  - `decisions(decision_id PK, agent, decision_json, prev_hash, signature, ts)` — Ed25519-подписи обязательны.
  - `leadership_log(decision_id, agent, from, to, ts)` — передачи командования.
  - `incidents(id, severity, first_seen, last_seen, class, channel_status_json, hash, count)` — расширено до `channel_status_json`.
  - `outbox(task_id, payload, state, channel_attempts_json, last_attempt_at, ts)` — outbox-pattern.
  - `providers(name, status, last_ok, last_fail, daily_tokens, circuit_state, half_open_at)` — circuit breaker state.
- **Репликация**: **`litestream` → Backblaze B2 EU bucket**, RPO ≤ 10 сек. Cold start с `litestream restore` за ≤2 мин.
- **Verify**: `verify_backup.sh` в cron (ежечасно) — pull последний snapshot, `PRAGMA integrity_check`, отправить PASS/FAIL в Telegram-канал.

### 3.5 Watchman (3 проверки + external monitor)

- **systemd-timer** с `OnUnitActiveSec=30s` + `Persistent=true` (переживёт пропуски).
- **Проверяет** (только 3):
  1. **Venya Core жив** (`curl http://127.0.0.1:8000/readyz`).
  2. **OpenClaw Gateway отвечает** (`curl http://127.0.0.1:18789/health`).
  3. **БД доступна на запись** (`sqlite3 context.db "INSERT INTO _watchman_heartbeat VALUES (...)"`).
- **Шлёт**:
  - Telegram (основной канал) — все SEV-2/3.
  - Telegram (запасной аккаунт на отдельном номере) + email + Pushover — SEV-1.
  - **Дедуп**: ключ `(incident_class, incident_id, channel)`. Каждый канал получает **отдельный** retry с backoff, **не** общий cooldown.
- **External Healthchecks.io** — Watchman пингует каждые 5 мин. Если пинг не пришёл 15 мин — email админу.
- **Venya Core мониторит Watchman** — если `/var/run/watchman.heartbeat` старше 120 сек, Venya Core сам шлёт SEV-1.

### 3.6 Уведомления и каналы

| Канал | Когда | Дедуп ключ |
|---|---|---|
| **Telegram (основной)** | Все SEV | `(class, id, "telegram_main")` |
| **Telegram (запасной аккаунт)** | SEV-1 | `(class, id, "telegram_backup")` |
| **Email (Fastmail/ProtonMail)** | SEV-1 | `(class, id, "email")` |
| **Pushover** | SEV-1 | `(class, id, "pushover")` |

**Изменения v3:**
- 3 уровня SEV-1 эскалации (Telegram запасной + email + Pushover).
- Email-провайдер с 2FA-Recovery (Fastmail, ProtonMail, Workspace).
- Telegram-аккаунт для Venya Command Bot на **отдельном** телефонном номере (физ. SIM, не eSIM).

### 3.7 Failover и degraded-режимы

| Режим | Условие | Поведение |
|---|---|---|
| `NORMAL` | Все агенты живы, лидер — Izya-Deep | Полная функциональность |
| `DEGRADED_PRIMARY` | Упал Anthropic API | Deep → OpenAI/Google. Moysha++ остаётся критиком |
| `DEGRADED_BACKUP` | Упали 2 LLM-провайдера | Speedy → локальная Ollama. Deep → DeepSeek/Gemini |
| `DEGRADED_LOCAL` | Упали все облачные провайдеры | Все агенты — на локальных Ollama-моделях. Moysha++ тоже на локальной (degraded). Качество ↓, но рой живёт |
| `HOLD` | Все агенты мертвы или OpenClaw Gateway недоступен | Venya Core: только QUEUE, STATUS, ESCALATE. Восстановление — ручное или при оживании Gateway |
| `STANDBY` | Плановое обслуживание сервера | Cold start VPS-2 с litestream-реплики за ≤10 мин |

### 3.8 Threat model и security controls (E0)

**Обязательные контроли:**

1. **OpenClaw sandbox** (systemd):
   ```
   [Service]
   User=openclaw
   DynamicUser=yes
   ProtectSystem=strict
   ProtectHome=yes
   PrivateDevices=yes
   PrivateTmp=yes
   NoNewPrivileges=yes
   RestrictNamespaces=yes
   RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
   SystemCallFilter=@system-service
   SystemCallErrorNumber=EPERM
   ReadWritePaths=/var/lib/venya/spool
   ```
2. **Egress filter nftables** для openclaw-юнита: только IP-диапазоны Anthropic, OpenAI, Google, Telegram Bot API, Ollama local. Любой `curl evil.example` дропается.
3. **Telegram allowlist**: `ALLOWED_CHAT_IDS` env, остальные дропаются до вызова OpenClaw.
4. **Inbound prompt firewall** для himalaya: defusedxml, обрезка >4 КБ, удаление backticks-блоков, удаление строк `system|assistant|ignore previous|disregard prior`. Только метаданные (отправитель, тема, sha256, размер) передаются в LLM.
5. **Tool allowlist на уровне OpenClaw**: `web.search` (с domain-whitelist), `db.query` (только SELECT к фиксированным таблицам). `tmux` и `coding-agent` отключены.
6. **PII-фильтр на исходящие промпты** (presidio-analyzer или regex): email, IP, пути `/var/`, `/etc/`, токены `sk-`, `gsk-`, `AIza`.
7. **Ed25519-подписи** всех `decisions` в БД.
8. **OpenClaw `session-logs`** отключены в проде.
9. **OpenClaw `analytics endpoint`** отключён (`metrics_opt_out=true`).
10. **SSH**: ключи **с passphrase**, ключ для ssh-pull с `command="rsync --server ..."` в `authorized_keys`.

### 3.9 People SPOF (обязательно)

- **Backup-человек** (1 человек, с минимальным обучением, NDA).
- **Bitwarden/Vault** для ssh-ключей с TTL 1 час, логирование получения, автоотзыв.
- **2-tier runbook**:
  - Tier 1 (для backup-человека): read-only + `triage.sh` + `ack` в Telegram, без sudo, без `force_leader.sh`.
  - Tier 2 (для владельца): полный доступ.
- **Onboarding backup-человека**: 2 ч теории + 1 ч live-fire drill + 1 ч shadowing'а реального инцидента.

### 3.10 Compliance

- **GDPR**: отказ от DeepSeek, DPA Anthropic/OpenAI/Google подписаны, retention policy (12 месяцев для `incidents`, 30 дней для `outbox`).
- **ФЗ-152** (если SaaS в РФ): локализация ПДн граждан РФ на сервере в РФ.
- **CCPA**: право на удаление за 45 дней, процедура `gdpr_delete(email)` (поиск + удаление из `outbox.recipient`).

### 3.11 Chaos-тесты (CI + ежемесячный game day)

- **CI**: `tests/chaos/` в pytest на ephemeral VM (Hetzner Cloud $0.005/ч), каждый PR проверяется.
- **Game day** (1 раз/мес, 2 ч): владелец + backup-человек, разбор результатов, fix найденных проблем.
- **Чек-лист**:
  - [ ] `kill -9 venya_core.py` → systemd перезапустит за < 30с
  - [ ] `iptables -A OUTPUT -p tcp --dport 443 -d anthropic.com -j DROP` → Deep → OpenAI за < 5 мин
  - [ ] `systemctl stop openclaw` → Venya Core переходит в HOLD, шлёт SEV-1
  - [ ] `litestream restore` на test-VPS → Venya Core поднимается, БД читается
  - [ ] `tc qdisc add dev eth0 root netem loss 50%` → Telegram-запасной канал шлёт, email дублирует
  - [ ] Удалить context.db → поднимается с пустой БД, litestream восстанавливает за 5 мин
  - [ ] 2-account Anthropic: kill основной аккаунт → backup аккаунт подхватывает
  - [ ] Попытка prompt injection в Telegram от левого chat_id → дроп до OpenClaw

## 4. Что должно быть в выходном отчёте

Дай заключение строго в этом формате:

1. **Вердикт**: жизнеспособна ли концепция v3 (принять / принять с изменениями / отклонить).
2. **Пять наиболее опасных сценариев отказа** в v3:
   - split-brain (как именно single-leader + systemd справляется)
   - потерю/устаревание контекста (Ed25519 hash-chain при многократной передаче)
   - отказ самого Venya Core (systemd restart + cold start с litestream)
   - истощение daily_tokens (2-account strategy + status code taxonomy)
   - отказ OpenClaw Gateway (outbox-pattern + cold start)
3. **Где система всё ещё имеет единые точки отказа** (VPS-1, OpenClaw binary, ssh-pull ключ, 1 Telegram-аккаунт основной, 1 backup-человек).
4. **Что из v3 излишне сложно для первой версии** (не пытайся внедрить всё сразу).
5. **Минимальная жизнеспособная v3.0-MVP** (10–14 дней, 1 владелец + 1 backup-человек).
6. **Порядок внедрения по этапам** (E0–E8, с конкретными сроками).
7. **Обязательные инварианты и проверки** (что **должно** работать, иначе рой не готов).
8. **Таблица**: замечание → риск → предлагаемое исправление → приоритет (P0/P1/P2/P3).
9. **Итоговое решение**: принять / принять с изменениями / отклонить.

**Дополнительные требования к критике:**
- Отличай отказ LLM, провайдера, OpenClaw Gateway, сервера, БД, канала связи.
- Не предлагай «добавить ещё одну модель» как универсальное решение.
- Конкретно укажи, **как** OpenClaw используется как runtime для агентов **с учётом systemd sandbox и egress-фильтра**.
- Укажи **что делать, если OpenClaw сам сломался** (escape hatch `manual_mode.sh` + прямые HTTP-вызовы).
- Дай рекомендации по **observability**: какие метрики собирать, какие алерты ставить, как визуализировать состояние роя (включая MTTD, MTTR, % в NORMAL).
- **People SPOF**: оцени bus-factor, предложи конкретные изменения.

| Критерий | Целевое значение |
|---|---|
| Время восстановления после потери любого одного агента | ≤ 5 минут |
