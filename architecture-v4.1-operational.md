# Architecture v4.1 Operational: Веня как единая диспетчерская

> Статус: целевая архитектура ближайшей реализации.
> Дата: 2026-06-18.
> Сервер: Ubuntu 24.04, 4 vCPU, 8 ГБ RAM, CPU-only.
> Основа: работающие Venya P0/P1-shadow, Student, Tesla, OpenClaw и Sliding Horizons.

## 0. Зачем нужна v4.1

v4 Lite закрыла отказ одного LLM, но после запуска Вени, Студента и Тесли
появился новый главный риск: состояние задачи находится сразу в нескольких
несвязанных местах.

Сейчас:

- Venya P0 хранит 7 зарегистрированных задач в JSON;
- Venya P1 SQLite работает только в shadow и содержит отдельное состояние;
- Sliding Horizons хранит 171 карточку в собственном JSON;
- Git `exchange/` хранит задания, отчёты и решения вручную;
- Tesla работает в отдельной ветке и пока не получает задачи из Venya Core.

Цель v4.1 — не добавить ещё один слой, а определить один авторитетный источник
для агентных задач и безопасно подключить к нему существующие компоненты.

## 1. Было → стало

### Было

```text
Telegram -> Venya P0 JSON
Telegram -> Student -> local Ollama
Telegram -> Tesla -> отдельная Git-ветка
Sliding Horizons -> собственный tasks.json
Git exchange -> отдельные task/report/decision-файлы
```

Каждый контур полезен, но полного жизненного цикла задачи нет ни в одном.

### Стало

```text
Александр
    |
    v
Venya Intake Bot
    |
    v
Venya Core P1 SQLite  <---->  Sliding Horizons adapter
    |                              |
    |                              +-- личные и календарные карточки
    |
    +--> Dispatcher --> Student worker
    |
    +--> Dispatcher --> Tesla worker --> Git artifacts
    |
    +--> Izya review / architecture / execution permit
    |
    +--> Delivery outbox --> Telegram reports
```

Venya Core P1 — единственный источник истины для агентных задач.

## 2. Границы контуров

### 2.1. Venya Core P1 — реестр агентных задач

Core хранит:

- постановку и стабильный `task_id`;
- владельца, исполнителя и источник;
- состояние и историю переходов;
- приоритет, срок, риск и блокировки;
- предложения исполнителя;
- решение Александра;
- допуск Изи к исполнению;
- доказательства результата;
- состояние доставки ответа.

Core не пишет красивые ответы и не решает задачу при помощи LLM.

### 2.2. Веня — единая точка входа и контроль

Веня:

1. принимает новую задачу Александра;
2. регистрирует её в Core;
3. возвращает квитанцию с `task_id`;
4. маршрутизирует по установленным правилам;
5. контролирует статус и сроки через Core и дашборд;
6. собирает результат и доставляет его Александру.

Веня не принимает архитектурных решений и не заменяет Изю.

### 2.3. Студент — локальный безопасный исполнитель

Студент получает:

- простые информационные задачи;
- локальную обработку текста;
- безопасные read-only проверки;
- аварийные ответы при недоступности облаков.

Студент не получает произвольный shell, root, deploy и архитектурные полномочия.

### 2.4. Тесля — аналитик и резервный инженер

Тесля:

- анализирует назначенную задачу;
- собирает проверяемые факты;
- предлагает варианты и рекомендацию;
- документирует предложение в `exchange/reports/tesla/`;
- выполняет допущенную реализацию в своей ветке;
- запускает тесты и возвращает доказательства.

До допуска к исполнению Тесля может менять только документы предложений.

Маркер допуска:

`ДОПУСК ИЗИ: ПРИНЯТО К ИСПОЛНЕНИЮ`

Тесля эскалирует неясность Вене, а нехватку компетенции, полномочий или
архитектурный вопрос — Изе с подготовленным пакетом фактов и вариантов.

### 2.5. Изя — архитектура, экспертиза и приёмка

Изя:

- принимает архитектурные вопросы;
- проверяет предложения исполнителей;
- даёт Александру рекомендацию;
- после решения Александра выдаёт ограниченный допуск к исполнению;
- принимает результат по доказательствам;
- проводит выволочку или выдаёт пряник по фактической работе.

Если Изя временно недоступен, Александр может выполнить экспертную оценку.
Новая реализация ждёт контрольного допуска Изи. Уже порученные, штатные и ранее
допущенные задачи продолжаются.

### 2.6. Sliding Horizons — представление, не реестр Core

Доска содержит два логических типа карточек:

1. `agent_task` — проекция задачи Venya Core;
2. `planning_item` — личная, календарная, информационная или бытовая карточка.

Для `agent_task` авторитетны Core и `task_id`. Доска может менять разрешённые
поля через API Core, но не хранит независимую копию жизненного цикла.

Для `planning_item` авторитетен собственный контур доски и внешние источники:
Google Calendar, Telegram Inbox, email и ручной ввод.

Одна визуальная доска может показывать оба типа, но их нельзя молча превращать
друг в друга.

### 2.7. Git — журнал и артефакты

Git хранит:

- предложения;
- отчёты и доказательства;
- решения;
- архитектурные документы;
- код и патчи.

Git не используется как realtime-очередь. Сначала транзакция фиксируется в
Core, затем асинхронный exporter публикует требуемый артефакт в Git.

## 3. Жизненный цикл задачи

Базовые состояния:

```text
RECEIVED
  -> ASSIGNED
  -> IN_PROGRESS
  -> PROPOSED
  -> WAITING_DECISION
  -> APPROVED
  -> IN_PROGRESS
  -> COMPLETED
```

Боковые состояния:

```text
BLOCKED
WAITING_INPUT
HOLD
FAILED
CANCELLED
```

Правила:

- задача не становится `COMPLETED` без доказательства;
- исполнение нового решения не начинается без решения Александра и допуска Изи;
- ранее допущенная штатная работа не требует повторного допуска;
- каждый переход записывается в append-only `task_events`;
- повторная команда с тем же idempotency key не создаёт дубль.
- triage, начало исполнения и verification фиксируются событиями, а не
  отдельными долговечными статусами.

## 4. Модель данных P1.1

Минимальные поля задачи:

- `id`;
- `title`, `description`;
- `task_type`: `analysis`, `implementation`, `ops`, `content`, `planning`;
- `source`, `external_id`, `idempotency_key`;
- `status`, `assignee`;
- `importance`, `urgency`, `manual_pin`, `risk`;
- `deadline`, `next_checkpoint_at`;
- `parent_id`, `blocked_by`;
- `requires_decision`, `decision_id`;
- `execution_permit_id`;
- `board_visibility`, `board_horizon`;
- `created_at`, `updated_at`.

Отдельные сущности:

- `task_events`;
- `task_artifacts`;
- `task_decisions`;
- `execution_permits`;
- существующие `task_outcomes`, `incidents` и `provider_circuits`.

Существующий delivery-state в `task_outcomes` используется как outbox до
выделения отдельной таблицы. Lease исполнителя хранится в задаче (`lease_owner`,
`lease_expires_at`), а не требует новой таблицы.

Глобальный «командирский мандат» P1 не используется для обычной выдачи работ.
Существующий механизм не удаляется в первом цикле: миграция сначала переиспользует
его там, где это безопасно, а упрощение выполняется после сквозного теста.

## 5. Маршрутизация

Маршрутизация процедурная:

- архитектура, безопасность, изменение ролей и интеграций -> `izya`;
- инженерный анализ, код, тесты, Git, техническая документация -> `tesla`;
- простая локальная обработка, безопасная справка и read-only задача -> `student`;
- неясная постановка -> `venya:WAITING_INPUT`;
- неизвестный класс или превышение полномочий -> `izya:TRIAGE`.

LLM может предложить классификацию, но окончательное назначение фиксирует
детерминированное правило либо Изя.

## 6. Приоритет и порядок исполнения

Core хранит отдельные измерения, а не одно магическое число:

- важность;
- срочность;
- дедлайн;
- ручное закрепление Александром.

Риск хранится отдельно как ограничение безопасности, но не смешивается с
очерёдностью. Блокирующее влияние вычисляется из зависимостей. Стоимость и
длительность добавляются позже только при практической необходимости.

## 7. Надёжность

### 7.1. LLM

- роль Изи по умолчанию использует `openai/gpt-5.5`;
- роль Тесли использует `ollama/minimax-m3:cloud`;
- роль Студента использует `ollama/qwen3.5:4b`.

Один отказ модели не должен останавливать регистрацию, контроль и доставку
статуса задачи.

Роль, полномочия и допуск не выводятся из имени модели. Смена модели не меняет
владельца решения и не расширяет разрешённые действия.

### 7.2. Хранилище

- P1 SQLite WAL;
- транзакции для задачи, события и outbox;
- резервная копия SQLite;
- offsite-копия после стабилизации схемы;
- P0 JSON сохраняется как rollback только на время перехода.

### 7.3. Доставка

Результат сначала фиксируется в `delivery_outbox`, затем отправляется в
Telegram. Повторная доставка идемпотентна.

### 7.4. Мониторинг

Watchman проверяет:

- OpenClaw;
- P1 Core;
- Venya bot;
- Student/Ollama;
- Tesla;
- Sliding Horizons;
- возраст последнего успешного утреннего доклада;
- размер очередей и количество просроченных задач.

Внешний Healthchecks.io контролирует исчезновение всего VPS. Пожары
дедуплицируются по классу, объекту и каналу. Пожар отправляется сразу.
Вечерний доклад создаётся только если пожар был.

## 8. Идентификаторы Core и Git

Core `task_id` вида `task-000001` является первичным идентификатором агентной
задачи во всех системах.

Git-файл может иметь человекочитаемое имя с датой и slug, но обязан содержать
поле `task_id`. Старый timestamp-id exchange protocol остаётся только для
legacy-файлов. Схемы и `exchange/README.md` обновляются на этапе контрактов.

## 9. Инварианты

1. Новая агентная задача получает один стабильный `task_id`.
2. Venya Core P1 — единственный авторитет состояния агентной задачи.
3. Доска и Git не создают независимую конкурирующую истину.
4. Исполнитель не может сам выдать себе архитектурное решение или permit.
5. `COMPLETED` требует проверяемого доказательства.
6. Результат не теряется между фиксацией и Telegram-доставкой.
7. Секреты не попадают в Git, отчёты и карточки.
8. Падение LLM не мешает принять задачу и сообщить её статус.
9. Переход P0 -> P1 имеет проверенный rollback.
10. Личные карточки доски не становятся агентными задачами без явного действия.
11. Git artifact всегда содержит первичный Core `task_id`.
12. Один пожар не создаёт повторные уведомления без изменения состояния.

## 10. Что не делаем в ближайшем цикле

- второй активный Core;
- распределённый consensus;
- автоматический LLM-командир;
- Kafka/RabbitMQ;
- полную замену Sliding Horizons;
- перенос всех 171 карточки в Core;
- сложный RBAC;
- автоматический deploy агентами.
- Ed25519-подпись каждой записи;
- формальный bus-factor ≥ 2.

Они возвращаются после рабочего сквозного контура и restore drill.

## 11. Критерий готовности v4.1

Система считается собранной, когда:

- задача, отправленная Вене, появляется в P1 и на доске с одним `task_id`;
- Веня назначает её Студенту, Тесле или Изе;
- исполнитель возвращает предложение или результат в Core;
- предложение Тесли появляется в Git;
- решение Александра и допуск Изи фиксируются отдельно;
- доска показывает фактический статус без ручного дублирования;
- итог доставляется один раз;
- утренний доклад строится из Core, здоровья сервисов и доски;
- controlled restart не теряет и не дублирует задачу.
- внешний heartbeat обнаруживает исчезновение VPS.
