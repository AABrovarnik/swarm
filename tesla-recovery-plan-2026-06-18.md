# План восстановления Тесли и контура поручений

Дата подготовки: 2026-06-18  
Владелец восстановления и приёмки: Изя  
Статус: план, изменения в live-сервисах ещё не выполнялись

## 1. Подтверждённые причины инцидента

1. `tesla-bot.service` запускается через `/usr/bin/node` версии 18.19.1.
   В этом runtime `fetch()` к Telegram завершается
   `UND_ERR_CONNECT_TIMEOUT`.
2. Закреплённый Node 22.22.2
   (`/opt/venya-runtime/node-v22.22.2`) под пользователем `moysha`
   успешно получает HTTP 200 от Telegram.
3. Тесля принимает задачи только через Telegram. Файл
   `exchange/inbox/tesla/REQUEST-TESLA-2026-06-18-001.json` бот не читает,
   поэтому публикация задания в Git не была доставкой.
4. Venya Core P1 работает в shadow на `127.0.0.1:8791`, но Тесля к нему
   не подключён. Executor bridge существует и проходит тесты, однако live-worker
   не развёрнут.
5. Watchman проверяет только `systemctl is-active` для Venya Command Bot.
   Он не проверяет Telegram polling, свежесть offset и Теслю, поэтому показывает
   зелёное состояние при функционально мёртвом боте.
6. Тесля уже создавал Markdown-отчёты локально, но они остались untracked.
   Runner запрещает `git push`, а доверенный exporter отсутствует.

Сопутствующий дефект: `venya-command-bot.service` также работает на Node 18 и
имеет те же ошибки `fetch failed`.

## 2. Что считается восстановлением

У восстановления четыре уровня:

- **R1 — связь:** бот получает Telegram update и отвечает.
- **R2 — выполнение:** Тесля подтверждает поручение, выполняет его и создаёт
  отчёт.
- **R3 — гарантированный контур:** поручение проходит машинно проверяемые
  состояния с claim/ACK, lease, timeout и эскалацией.
- **R4 — штатная эксплуатация:** Веня регистрирует задачу в live Core, Тесля
  забирает её, результат публикуется доверенным exporter, Watchman контролирует
  функциональное здоровье.

`systemd active` не является критерием ни одного уровня.

Оценка работ: 30–45 минут  
Ответственный: Изя

Работы:

1. Снять резервные копии unit-файлов Тесли и Вени.
2. Заменить `ExecStart=/usr/bin/node` на закреплённый
   `/opt/venya-runtime/node-v22.22.2`.
3. Выполнить `systemctl daemon-reload` и контролируемый restart сначала Тесли,
   затем Вени.
4. Не менять токены, allowlist и код задачи.

Приёмка:

- `getMe` успешен из-под сервисного пользователя;
- в журнале нет `UND_ERR_CONNECT_TIMEOUT` 10 минут;
- Telegram offset меняется после тестового сообщения;
- `/status` получает ответ;
- ответ содержит правильную ветку и наличие локальных изменений.

Rollback:

- вернуть резервную копию unit;
- сервис оставить остановленным, если функциональная проба не прошла;
- не объявлять восстановление по одному `active (running)`.

### Этап B. Вернуть выполнение текущего поручения — R2

Срок: **2026-06-18 20:30 МСК**  
Ответственные: Изя — доставка и приёмка; Тесля — анализ и отчёт

Работы:

1. Повторно выдать `REQUEST-TESLA-2026-06-18-001` через работающий канал.
2. Получить явный ACK с `task_id`, понятым результатом и сроком.
3. Запустить выполнение в режиме анализа без live-изменений.
4. Проверить отчёт и связанные доказательства.
5. Доверенным процессом, не LLM, закоммитить и запушить принятый отчёт.

Приёмка:

- ACK не позднее 2 минут после доставки;
- статус `ИСПОЛНЯЮ` содержит checkpoint;
- отчёт имеет исходный `task_id`;
- отчёт доступен на GitHub и указан commit SHA;
- Александр получает ссылку и итог проверки.

Стоп-условия:

- нет ACK;
- задача не понята или потерян `task_id`;
- отчёт появился только локально и не опубликован;
- Тесля менял файлы вне разрешённого каталога.

### Этап D. Shadow-контур Core → Тесля — R3

Срок: **2026-06-19 18:00 МСК**  
Ответственный: Изя; Тесля — shadow-worker

Работы:

1. Расширить контракт задачи полями `assignee`, `attempt_id`, `deadline`,
   `next_checkpoint_at`, `lease_owner`, `lease_expires_at`.
2. Зафиксировать переходы:
   `RECEIVED -> ASSIGNED -> ACKNOWLEDGED -> IN_PROGRESS -> SUBMITTED
   -> ACCEPTED`.
3. Добавить боковые состояния `REJECTED`, `BLOCKED`, `FAILED`, `EXPIRED`.
4. Подключить Tesla worker к P1 shadow:
   - claim только `assignee=tesla`;

Приёмка:

- тестовая задача проходит полный путь без ручного переноса текста;
- повтор доставки не создаёт дубликат;
- restart между claim и outcome возвращает задачу после TTL;
- задача без permit не меняет рабочие файлы;
- все переходы присутствуют в append-only `task_events`.
