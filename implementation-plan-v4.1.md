# План реализации Architecture v4.1

> Принцип: сначала один реестр задачи и сквозной минимальный путь, затем удобство.
> Оценка: 3–4 рабочих дня до первого сквозного маршрута;
> 10–15 рабочих дней до полной v4.1 с доской, тестами и восстановлением.

## Текущее состояние

Работает:

- Venya P0 на `127.0.0.1:8790`, 7 задач;
- Venya P1-shadow на `127.0.0.1:8791`, SQLite;
- Student через независимый Telegram-бот и локальный Qwen;
- Tesla через `@OwlTeslyaBot`, MiniMax M3 и ветку `tesla/engineering`;
- Sliding Horizons на `127.0.0.1:8787`, 171 JSON-карточка;
- Git exchange;
- OpenClaw с OpenAI, MiniMax и локальным fallback.

Не работает сквозным образом:

- Веня не назначает задачи исполнителям;
- исполнитель не возвращает структурированный статус Вене;
- P1 не является live Core;
- доска не читает Core;
- Git-артефакт не связан транзакционно с `task_id`;
- Google Calendar интеграция доски имеет `invalid_grant`;
- импорт cron в доске читает legacy-файл, уже перенесённый OpenClaw в SQLite;
- утренний cron остаётся на старом расписании и ранее падал по лимитам.

## Этап 0. Зафиксировать контракты

Срок: 0.5 дня.

- принять `architecture-v4.1-operational.md`;
- принять временный регламент ролей;
- обновить task/report schemas;
- сделать Core `task_id` первичным идентификатором Git artifacts;
- определить поля приоритета, статусы и правила переходов;
- сохранить снимок P0 и P1;
- добавить smoke-команды и rollback checklist.

Критерий:

- поля и переходы не трактуются по-разному Core, ботом и доской.

## Этап 1. Venya P1.1 как live Core

Срок: 2 дня.

- добавить в SQLite поля назначения, приоритета, решения, permit и board projection;
- переиспользовать существующие outcomes/incidents/circuits, не создавать дубли;
- добавить endpoints:
  - `GET /tasks`;
  - `GET /tasks/:id`;
  - `PATCH /tasks/:id`;
  - `POST /tasks/:id/assign`;
  - `POST /tasks/:id/status`;
  - `POST /tasks/:id/artifacts`;
  - `POST /tasks/:id/decision`;
  - `POST /tasks/:id/permit`;
- мигрировать 7 P0-задач в чистую P1;
- переключить Venya bot с `8790` на `8791`;
- оставить P0 остановленным, но доступным для rollback.

Проверки:

- idempotency;
- миграция повторно не создаёт дубли;
- restart сохраняет состояние;
- rollback возвращает бота на P0.

## Этап 2. Диспетчер Вени

Срок: 1–2 дня.

- добавить triage при регистрации;
- назначать `student`, `tesla` или `izya`;
- неясные задачи переводить в `WAITING_INPUT`;
- вернуть Александру квитанцию: `task_id`, исполнитель, приоритет, следующий checkpoint;
- добавить `/task`, `/tasks`, `/task <id>`, `/blockers`.

Сначала маршрутизация правилами. LLM-классификатор — только необязательная
подсказка.

Проверки:

- пять типовых задач получают ожидаемого исполнителя;
- неизвестный тип не исполняется молча;
- архитектурная задача всегда попадает Изе.

## Этап 3. Мост к Тесле

Срок: 1–2 дня.

- Tesla worker claims только задачи с `assignee=tesla`;
- lease ограничена одной задачей и TTL;
- анализ создаёт Markdown в `exchange/reports/tesla/`;
- путь и summary записываются в Core как artifact;
- без permit рабочие файлы не изменяются;
- после permit реализация, тесты и evidence возвращаются в Core;
- Telegram-бот Тесли остаётся аварийным прямым каналом, не штатной точкой входа.

Проверки:

- задача проходит `ASSIGNED -> IN_PROGRESS -> PROPOSED`;
- Git-документ содержит тот же `task_id`;
- отсутствие permit не меняет рабочие файлы;
- эскалация содержит факты, варианты и конкретный вопрос.

## Этап 4. Мост к Студенту

Срок: 0.5–1 день.

- Student claims только разрешённые простые/read-only задачи;
- сохраняет summary и evidence;
- при нехватке возможностей переводит задачу в `BLOCKED` или `WAITING_INPUT`;
- не выдаёт совет за выполненное действие.

Проверки:

- локальная задача выполняется без OpenAI и MiniMax;
- опасная или архитектурная задача не исполняется;
- результат возвращается Вене.

## Этап 5. Sliding Horizons read-only adapter

Срок: 1–2 дня.

- добавить источник `venya_core`;
- показывать `agent_task` с `task_id`, assignee, status, priority и checkpoint;
- не копировать Core-задачи навечно в `tasks.json`.
- личные `planning_item` продолжают жить в контуре доски.
- заменить чтение legacy cron-файла на поддерживаемый OpenClaw API/export.

Проверки:

- одна задача не удваивается после refresh/import;
- статус на доске совпадает с Core;
- личная карточка не попадает в очередь агентов автоматически.

Controlled write-back доски выполняется отдельным следующим этапом после недели
наблюдения read-only проекции.

## Этап 6. Решения, допуски и Git

Срок: 1 день.

- решение Александра записывать отдельно от предложения;
- допуск Изи создавать как отдельный permit с task id, scope и ограничениями;
- exporter публикует decision/report в Git после commit в Core;
- merge в Git не заменяет состояние Core.

Проверки:

- Тесля не может сама создать действующий permit;
- permit относится к одной задаче и ограниченному scope;
- evidence результата связано с решением.

## Этап 7. Доклады и пожары

Срок: 0.5 дня.

- утренний доклад ежедневно в 09:00 Europe/Moscow;
- источник: Core, health сервисов, свежие Git artifacts и planning board;
- MiniMax M3 как независимая модель форматирования;
- при отказе LLM отправляется процедурный шаблон;
- пожар отправляется сразу;
- вечерний доклад — только если пожар был.

Проверки:

- отключение OpenAI не отменяет доклад;
- устаревший статус явно помечается;
- повтор одного пожара дедуплицируется.

## Этап 8. Надёжность и восстановление

Срок: 2 дня после стабилизации.

- backup SQLite;
- offsite replication;
- restore drill;
- внешний heartbeat;
- controlled restart Gateway/Core/Ollama/Tesla;
- проверить дренирование outbox и отсутствие дублей.

## Этап 9. Сквозные тесты

Срок: 1 день, частично параллельно предыдущим этапам.

- happy path `Веня -> Тесля -> предложение -> решение -> permit -> результат`;
- локальный путь через Студента;
- restart Core между claim и outcome;
- повтор Telegram update;
- orphan Git artifact;
- повреждённый/занятый SQLite;
- отказ OpenAI, MiniMax и Telegram delivery;
- rollback P1 -> P0.

## Порядок ближайших действий

1. Утвердить v4.1 и временный регламент.
2. Расширить схему P1 до P1.1.
3. Перенести 7 P0-задач и переключить Venya bot.
4. Сделать один сквозной маршрут `Веня -> Тесля -> предложение -> Веня`.
5. Подключить read-only проекцию Core на Sliding Horizons.
6. Добавить Student worker.
7. Добавить решения/permits.
8. Закрыть доклады, пожары, тесты и recovery.
9. После недели наблюдения решить, нужен ли write-back доски.

## Стоп-условия

Не переходить к следующему этапу, если:

- задача теряется или дублируется;
- два хранилища считают себя авторитетными;
- статус меняется без события;
- исполнитель может расширить собственные полномочия;
- доска меняет Core в обход API;
- rollback не проверен.
