# Architecture v4 Lite: доступный дублёр без единой точки отказа LLM

> Статус: реализация MVP.
> Дата: 2026-06-18.
> Целевой сервер: Ubuntu 24.04, 4 vCPU, 8 ГБ RAM, без GPU.
> Долгосрочная архитектура: `architecture-v3.md`; этот документ её не заменяет.

## 0. Цель

Закрыть конкретный отказ: основной LLM исчерпал лимит, поэтому чат, cron-задачи
и служебные проверки одновременно перестали давать полезный результат.

MVP считается успешным, если:

1. при rate limit OpenAI запрос автоматически уходит другому провайдеру;
2. при недоступности всех облаков отвечает локальная модель;
3. служебные cron-задачи выполняют сбор фактов без LLM;
4. задача не теряется при рестарте Gateway;
5. владелец получает один понятный статус вместо серии одинаковых ошибок.

## 1. Основной принцип

LLM — исполнитель, но не оркестратор надёжности.

Режим, очередь, circuit breaker, дедупликация и выбор маршрута определяются
процедурным кодом или конфигурацией OpenClaw. Ни одна модель не должна решать,
доступна ли она сама.

## 2. Состав MVP

### 2.1. Контур диалога

Порядок моделей:

1. `openai/gpt-5.5` — основной интеллектуальный агент;
2. `minimax/MiniMax-M3` — независимый облачный дублёр после подключения API;
3. `ollama/qwen3.5:4b` — локальный аварийный дублёр без интернета.

До подключения MiniMax допустима временная цепочка:

`openai/gpt-5.5 -> ollama/qwen3.5:4b`.

Локальная модель работает с concurrency=1. Все роли используют одну очередь,
а не держат несколько моделей в памяти одновременно.

### 2.2. Два профиля полномочий

`izya-engineer`:

- доступен только владельцу в доверенном личном канале;
- может использовать инженерные инструменты;
- сложные или необратимые действия требуют явного разрешения.

`izya-duty`:

- используется при деградации и для фоновых проверок;
- read-only по умолчанию;
- разрешены status, health, чтение очереди и отправка служебного отчёта;
- shell, произвольная запись файлов и внешние публикации запрещены.

Модель и полномочия не должны быть связаны. Переход на более слабую модель
не выдаёт ей дополнительные права и не снимает существующие ограничения.

### 2.3. Процедурные задания

Утренние сводки, backup-check и security-check состоят из двух частей:

1. скрипт собирает структурированные факты;
2. LLM опционально форматирует текст.

Если LLM недоступна, отправляется шаблонный отчёт из собранных данных. Проверка
не должна считаться проваленной только из-за отсутствия красивой формулировки.

### 2.4. Хранилище состояния

В MVP используются отдельные сущности:

- `tasks` — пользовательские и фоновые задания;
- `delivery_outbox` — сообщения, ожидающие доставки;
- `incidents` — дедупликация и история сбоев;
- `provider_state` — circuit breaker и время последнего успешного запроса.

Git-репозиторий не является realtime-очередью. Он служит долговечным,
проверяемым человеком журналом заданий, отчётов и архитектурных решений.
Live-очередь должна храниться в SQLite.

## 3. Режимы

`NORMAL`:

- OpenAI доступен;
- полный интерактивный режим.

`DEGRADED_CLOUD`:

- OpenAI недоступен;
- запросы идут в MiniMax M3;
- пользователь получает одно уведомление о переключении.

`DEGRADED_LOCAL`:

- облачные провайдеры недоступны;
- запросы последовательно обслуживает Qwen;
- разрешены только безопасные задачи и read-only инструменты.

`HOLD`:

- ни одна модель не отвечает либо Gateway недоступен;
- новые задания сохраняются в очередь;
- процедурные проверки и аварийные уведомления продолжают работать.

## 4. Failover

Circuit breaker открывается после классифицированной ошибки:

- rate limit / provider cooldown;
- timeout;
- 5xx;
- invalid or expired credentials;
- provider unavailable.

Ошибки пользователя и политики безопасности не являются основанием для
автоматического перехода к другой модели.

Начальные параметры:

- 2 последовательные provider-ошибки открывают circuit на 15 минут;
- повторная проверка выполняется одним half-open запросом;
- после успеха circuit закрывается;
- повторяющиеся уведомления дедуплицируются на 60 минут.

## 5. Watchman

Локальный systemd timer проверяет:

1. `http://127.0.0.1:18789/health`;
2. Ollama `http://127.0.0.1:11434/api/version`;
3. возраст последнего успешного cron-запуска;
4. размер очередей `tasks` и `delivery_outbox`.

Heartbeat хранится как атомарно обновляемый файл или одна строка SQLite через
UPSERT. Нельзя добавлять новую строку каждые 30 секунд без ротации.

Внешний Healthchecks.io контролирует пропажу всего VPS. Мониторинг на том же
сервере не считается внешним.

## 6. Восстановление

SQLite реплицируется через Litestream в S3-compatible storage.

Для восстановления одного файла БД недостаточно. Репозиторий должен содержать:

- provisioning manifest или Ansible playbook;
- systemd units;
- список закреплённых версий;
- инструкции восстановления секретов;
- smoke-test после deploy.

Секреты запрещено хранить в Git. Используются OpenClaw SecretRefs и systemd
`LoadCredential=`.

## 7. Git как канал обмена

Каталог `exchange/` используется для асинхронного обмена:

- человек создаёт task-файл;
- агент публикует report-файл;
- принятое решение переносится в `decisions/`;
- секреты, токены и сырые личные данные не коммитятся.

Формат описан в `exchange/README.md` и JSON Schema в `schemas/`.

## 8. Этапы внедрения

### E0 — немедленный дублёр

- установить `qwen3.5:4b`;
- добавить `ollama/qwen3.5:4b` в fallback OpenClaw;
- проверить запрос при принудительно недоступном primary;
- проверить Telegram-доставку результата.

### E1 — независимый облачный провайдер

- подключить MiniMax API через SecretRef;
- поставить MiniMax между OpenAI и Ollama;
- установить бюджетный лимит и circuit breaker;
- провести controlled failover test.

### E2 — процедурные cron-задачи

- вынести сбор фактов из LLM-промптов в скрипты;
- сохранять JSON-результат;
- отправлять сырой шаблон при отказе всех моделей.

### E3 — очередь и Watchman

- добавить SQLite `tasks`, `delivery_outbox`, `incidents`, `provider_state`;
- добавить systemd timer и внешний heartbeat;
- проверить рестарт Gateway и дренирование очереди.

### E4 — восстановление

- Litestream + offsite storage;
- provisioning;
- restore-drill;
- второй канал SEV-1.

## 9. Что сознательно отложено

- три параллельных LLM-агента;
- Ed25519-подпись каждой строки;
- четыре облачных провайдера;
- второй активный Venya Core;
- Prometheus/Grafana/Loki;
- автоматический выбор «командира» среди LLM;
- сложная многоуровневая IAM-модель.

Они возвращаются только после измеренного ограничения MVP.

## 10. Критерии готовности

- локальный fallback отвечает через OpenClaw;
- контролируемый rate-limit не приводит к технической ошибке пользователю;
- cron выдаёт полезный отчёт без LLM;
- после `kill` Gateway сохранённая задача выполняется один раз;
- при остановке VPS внешний монитор сообщает об этом;
- в репозитории нет секретов;
- recovery runbook проверен на чистой машине.
